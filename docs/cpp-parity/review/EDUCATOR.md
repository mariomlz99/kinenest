## Findings, in priority order

- **P2 — first subscription hint does not fit the supplied member-function scaffold.** `public/lessons/session-02-01-subscriber.json:12` gives `create_subscription<sensor_msgs::msg::LaserScan>("/scan", 10, receive)` in all seven languages, while line 118 defines `receive` as a nonstatic `Reader` member. Copying this into the constructor still requires an object-bound callable. Narrow correction: make the final C++ hint show `[this](sensor_msgs::msg::LaserScan::SharedPtr msg) { receive(msg); }`. This supplies callback plumbing while leaving beam interpretation/output to the learner. Source-level C++ mismatch; no fresh compiler reproduction was run. It does not undermine reference-program PASS evidence.
- **P3 — localization coverage does not imply equal hint depth.** In `session-05-01-odometry.json:127`, English ends with the general quaternion-to-yaw expression; NL/FR at lines 141/155 end with only a unit reminder. Their earlier planar formula suffices here, so this is not a solvability blocker. English/ES/DE/PT/IT learners receive an additional transfer concept. Consider matching that optional final explanation. Similarly, NL/FR 3.6 omit the explicit normalized proportional error and numeric speed bound supplied in the other languages. Existing qualitative guidance is usable; avoid claiming identical scaffolding in every language.

## What works pedagogically

- **Same concept, language-appropriate work:** 3.2 keeps shape/channel means as the outcome. Python learns CvBridge/NumPy; C++ teaches rgb8 bytes, row stride, channel indexing and double accumulation (`session-03-02-image-data.json`, programming.cpp.content and starterCode). A synthetic NumPy translation or mandatory native OpenCV would dilute this progression. 3.3–3.4 reuse thresholds/counts and accumulated x-coordinates, followed by visual steering in 3.6.
- **Scaffolding preserves student work:** 23 starters retain TODOs for relevant calculations, endpoints or callback behavior. Earlier plumbing is supplied when a later concept becomes the target: 4.5 already sends the goal and handles results but leaves feedback to implement; 6.3 provides endpoints/state slots while leaving perception, safety and control unfinished. This is sensible worked-example fading.
- **Optional cancellation is preserved:** `session-04-06-cancel.json:24` remains optional. C++ content distinguishes cancellation request from terminal result, requires a retained accepted handle and guards repeated requests. Supplying result-printing code focuses effort on lifecycle reasoning.
- **Diagnostic starters should stay faulty:** 6.1 publishes to `/velocity` (`session-06-01-topic-debug.json:135`); 6.2 requests the target in `odom` before using its coordinates as local steering error (`session-06-02-frame-debug.json:123`). These complete programs intentionally contain the fault under investigation. Hints progress from evidence/concept to correction. Removing the faults or replacing them with TODOs would weaken the objective.
- **Progression is coherent:** callbacks/state → sensor reductions → perception → services/parameters/actions → pose/frames → closed-loop control → diagnosis/integration. TF lessons distinguish target/source semantics and availability; 5.6 explicitly names reactive control and asks learners to discuss its limits.
- **Hints mostly progress usefully:** 3.2 moves from units to indexing to accumulation type; 3.3 from color reasoning to traversal to thresholds; 6.1 from a valid-but-wrong topic to graph inspection to expected topic. EN/NL/FR/ES/DE/PT/IT entries exist for all 25 exercises. This is not native-speaker linguistic certification or an observed classroom usability study.

## Tradeoffs and limits

Keep the class/handle/lambda scaffolding despite its length: it exposes ownership and callback shapes while TODOs isolate robotics reasoning. I would disagree with a blanket demand for shorter convenience APIs. Conversely, native-looking syntax must not be sold as native ROS fidelity: `docs/CPP.md` explicitly documents the educational executor, action request IDs, latest-planar TF, tracked buffers and report hooks. These limits make concept parity defensible; they do not establish package-build or hardware-transfer competence.

The final 5.6 hint gives a prescriptive 15-tick bypass policy. That reduces algorithm-design freedom but is a reasonable introductory integration aid and is shared with Python. Retain discussion of its limits rather than broadening this frozen candidate into a navigation curriculum. Behavioral PASS supports execution correctness; explanation prompts and lecturer observation remain necessary to establish understanding.
